1. **Accepted — P1: overlapping project opens can activate the wrong project.** Home’s sample and recent-project controls remain enabled during another open; completions unconditionally replace project identity and clear shared busy state. Start A, then B, and let A finish last. This is a reachable navigation race. **Safe fix:** one navigation transaction/request ID covering every entry point and completion, with consistent busy guards. [Home controls](/home/olhapi/projects/video-creater/src/components/workspace/project-home.tsx:91), [open handlers](/home/olhapi/projects/video-creater/src/App.tsx:369).

2. **Accepted — P1: that race can cross the editor’s project-state boundary.** After the first completion mounts the editor, the second updates its props without remounting. Local history, selections, and timeline view state survive; the persistence effect can write the old view state under the new directory’s key. Ordinary sequential navigation through Home unmounts the editor, so do not describe every project switch as affected. **Safe fix:** key the session by normalized directory plus project ID, retaining it across Settings for the same identity. Pair this with async cancellation. The mixed-directory/project preview call is real, but **canonical disk corruption is not established**: Rust reloads an existing saved project before preparing it. 3. **Accepted, reframed — P2: native-menu ownership fails across Settings.** The stronger trigger requires no IPC reordering: open Settings, then return without changing editor capabilities. App publishes inactive state on entry and publishes nothing on return; the retained editor’s menu effect has no active-view dependency. Conversely, background project changes can make the hidden editor publish active capabilities during Settings. **Reject reversed promise settlement as proof of reversed native application**: the Rust command is synchronous, and completion order alone proves neither. **Safe fix:** one App-owned publisher derived from current view and editor capabilities; gate editor command dispatch by active view. That native item stays enabled, App increments the external request ID, and the same Settings instance retains its preferred internal target. “Permanently” should mean **until remount**, not across sessions. **Safe fix:** associate internal navigation with the external request version that created it; supersede it whenever a new external request arrives. Comparing independently incremented counters numerically is insufficient. **Staged architectural direction:** first contain project transitions with request IDs, keyed sessions, and lifetime guards. Next centralize active-view ownership for native menus, shortcuts, and Settings navigation. Then consolidate preview availability into a typed render plan and separate media transport from clock correction. Keep canonical mutation and validation in Rust; introduce focused regression coverage alongside each fix rather than undertaking a broad frontend rewrite.
